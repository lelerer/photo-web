XAI Tester
Developer Guide

XAI Tester is a Python framework for running human-subject XAI evaluation experiments. Participants review raw data, an AI prediction, a ground-truth outcome, and feature-attribution explanations — then predict the AI's label. The entire framework runs on three collaborating modules: control, design, and io.

Python ≥ 3.10 zero dependencies 58 tests passing CSV + summary output
00

Architecture

The three modules have distinct, non-overlapping responsibilities. They collaborate through a shared active experiment object that is registered once and implicitly used by all subsequent calls.

01
control

The director. Manages the entire session lifecycle — from initialisation to teardown — and orchestrates the other two modules in the correct order.

02
design

The data layer. Defines the three-level hierarchy (Experiment → Session → Trial), loads CSV data, and handles feature-name and label mapping.

03
io

The stage and archive. Renders each trial to participants, collects their typed response, measures reaction time, and writes all data to disk.

The precise boundary of each module's responsibilities:

control owns
  • Validating that trials have been loaded
  • Registering the global active-experiment reference
  • Prompting for participant ID
  • Triggering the instructions screen
  • Resetting the clock to session start
  • Writing files and cleaning up at the end
design owns
  • Parsing CSV columns into Trial objects
  • Mapping v0–v5 to readable feature names
  • Mapping integer y values to label strings
  • Shuffling trial order on load
  • Storing features, attributions, AI labels
  • Computing is_correct / ai_agrees
io owns
  • Rendering 4 display blocks per trial
  • Reading the participant's free-text input
  • Precisely measuring reaction time
  • Appending a CSV row on every answer
  • Generating the summary report at end
  • Providing a swappable display-backend interface
01

Quick Start

A complete wine-quality XAI evaluation session in a single script:

from xai_tester import control, design, io, misc

# ── 1. design: define structure, load data ───────────────────
exp = design.Experiment(
    name   = "WineQuality_XAI",
    labels = ["Bad Quality", "Good Quality"],
)
exp.load_csv_fixed(
    "wine_quality.csv",
    feature_names = ["Vinegar Taint", "SO2", "pH",
                     "Sulphates", "Alcohol", "Others"],
    label_map     = {0: "Bad Quality", 1: "Good Quality"},
)

# ── 2. control: initialise, start session ────────────────────
control.initialise(exp)
control.start(participant_id="P01")

# ── 3. trial loop: io presents, collects, records ────────────
for i, trial in enumerate(exp.session.trials, start=1):
    trial.presented_at = exp.clock.session_time

    io.present_trial(trial,
                     trial_number = i,
                     total_trials = exp.session.n_trials,
                     labels       = exp.labels)

    exp.clock.reset()
    response, rt = io.get_response(trial)
    exp.data.record(trial, response, rt)

# ── 4. control: end, write summary ───────────────────────────
control.end()

The golden rule: design comes first (define structure), control drives the flow (initialise → start → end), and io lives inside the loop (display → collect → record). The calling order is fixed and cannot be reversed.

03

control — Session Flow

xai_tester.control is the framework's process orchestrator. It holds no experiment data and renders nothing directly. Its sole job is to invoke the other two modules in the right order at the right time.

Internally, the module maintains a single module-level variable _active_exp. Once initialise(exp) is called, the experiment is globally registered and every subsequent control function operates on it implicitly — no argument passing required.

Single-instance constraint. Only one experiment can be active at a time. Calling initialise() twice on the same object raises RuntimeError. After end() completes, the active reference is cleared and a new session can begin.

The four functions

initialise(experiment)

The first lifecycle call. It does exactly three things: validates that at least one Trial has been loaded (raises ValueError otherwise), creates the session Clock, and registers experiment as _active_exp.

It does not create any output files and does not prompt for a participant ID — those happen in start().

ParameterTypeDescription
experimentExperimentThe experiment to activate. Must have already called load_csv() or load_csv_fixed().
 
# Data must be loaded before initialising
exp = design.Experiment(name="Demo")
exp.load_csv_fixed("data.csv", feature_names=[...], label_map={...})
control.initialise(exp)   # exp.clock is now available

start(participant_id, auto_id, skip_instructions)

The true session launch point. Executes in sequence: obtain participant ID → create Session → create DataRecorder (which also creates the output directory on disk) → show instructions screen → reset clock to session start.

After this call, exp.session, exp.data, and exp.clock are all live and ready to use.

ParameterDefaultDescription
participant_idNoneExplicit ID string or integer. If None and auto_id=False, prompts via terminal input.
auto_idFalseAuto-generate a timestamp-based ID: auto_1704067200.
skip_instructionsFalseSkip the instructions screen — commonly used during development and testing.

pause(message)

Insert a rest-break screen mid-session. Blocks until the participant presses Enter. Typically placed at the halfway point of the trial loop. Internally just calls io.presenter.show_message(message).

for i, trial in enumerate(exp.session.trials, start=1):
    # ... trial logic ...
    if i == exp.session.n_trials // 2:
        control.pause("Halfway done — take a short break!\n\nPress Enter to continue.")

end(show_summary, goodbye_text)

The session endpoint. Executes in sequence: record session end time → call exp.data.save_summary() → optionally print the summary to stdout → show goodbye screen → clear _active_exp.

ParameterDefaultDescription
show_summaryTruePrint the summary report to stdout before the goodbye screen.
goodbye_textNoneOverride misc.defaults.goodbye_text.

Why does control hold no state of its own? The only state it tracks — _active_exp — is just a reference to the design.Experiment object. All experiment data lives in the design layer; all file operations belong to the io layer. This makes control a pure orchestrator that can be extended or replaced without touching either of the other modules.

04

design — Data Layer

xai_tester.design is the framework's data layer. It defines the three-level hierarchy, loads and parses experiment data, and exposes computed properties that the other modules consume.

Three-level hierarchy

Experiment         # top-level container: config + all Trials
  └── Session      # single run: one participant's complete session
        └── Trial  # single trial: one CSV row's full state

class Experiment

The top-level container, constructed before control.initialise() and used for the lifetime of the script. Holds all Trial objects and, after control.start(), exposes session, data, and clock.

exp = design.Experiment(
    name             = "WineQuality_XAI",
    labels           = ["Bad Quality", "Good Quality"],
    filename_suffix  = "pilot",          # appended to output filenames
    randomise_trials = True,             # shuffle on load
)

Three loading methods

MethodWhen to use
load_csv_fixed() Standard input: CSV with y, v0–v5, a0–a5 columns. Recommended for all new experiments.
load_fixed_format() You already have a list of dicts in memory (e.g. after manually parsing a .numbers file) — uses the same y/v/a convention.
load_csv() Flexible mode: arbitrary column names, with explicit ai_label_col, xai_cols, feature_cols.

How load_csv_fixed maps columns to Trial attributes:

# CSV column    →  key used inside Trial
# y             →  trial.ai_label           (converted via label_map)
# v0            →  trial.features["Vinegar Taint"]
# v1            →  trial.features["SO2"]
# ...           →  ...
# a0            →  trial.xai_scores["Vinegar Taint"]
# a1            →  trial.xai_scores["SO2"]
# ...           →  ...

exp.load_csv_fixed(
    "wine_quality.csv",
    feature_names    = ["Vinegar Taint", "SO2", "pH",
                        "Sulphates", "Alcohol", "Others"],
    label_map        = {0: "Bad Quality", 1: "Good Quality"},
    ground_truth_col = "gt",   # optional: real-world outcome column
    max_rows         = 20,     # optional: load only the first N rows
)

class Trial

The core data structure of the design layer. Each instance maps to one CSV row and simultaneously carries display data (read by the io module) and response data (written by the io module).

AttributeTypeSourceDescription
trial.featuresdictv0–v5Raw feature values, keyed by the readable names in feature_names. Displayed to participants in the Original Data block.
trial.xai_scoresdict[str,float]a0–a5Attribution scores, same keys. Positive = pushes toward positive class; negative = pushes away.
trial.ai_labelstry columnAI predicted label (converted via label_map). Shown to participants and used for scoring.
trial.ground_truthstr | Noneoptional colReal-world outcome. Shown alongside the AI label with ✓/✗. None if not provided.
trial.responsestr | Nonewritten by ioParticipant's typed answer. None until recorded.
trial.response_timefloat | Nonewritten by ioReaction time in seconds, from prompt display to Enter.
trial.presented_atfloat | Noneset manuallySession-clock value when the trial appeared. Set in the loop: trial.presented_at = exp.clock.session_time

Two computed properties

PropertyReturnsDescription
trial.is_correct bool | None Whether the participant's response matches ai_label (case-insensitive). Returns None before any response is recorded. Measures how well participants can predict the AI's decision.
trial.ai_agrees bool | None Whether ai_label matches ground_truth. Returns None when no ground truth was provided. Measures the AI's own accuracy, and enables the key cross-analysis with is_correct.

Why the cross-analysis matters. The summary report splits participant accuracy into two groups: trials where the AI was correct, and trials where it was wrong. If participants are worse at predicting the AI's label precisely when the AI itself was wrong, it indicates the XAI explanation failed to flag the AI's errors — the most important finding in XAI human-evaluation research.

class Session

Created automatically by control.start(). Access via exp.session. A runtime container for the Trial list; holds no raw data, just progress and timing information.

PropertyDescription
session.trialsOrdered list of Trial objects — iterate this to drive the trial loop.
session.n_trialsTotal number of trials.
session.n_completedNumber of trials with a recorded response (updates in real time).
session.durationTotal session time in seconds; None until control.end() is called.
05

io — Display & Record

xai_tester.io is the framework's perception and recording layer. It handles two very different but complementary jobs: outward display (showing trial content to participants) and inward recording (persisting their answers to disk).

The display side is implemented via a swappable presenter object; the recording side via a DataRecorder. The two are independently designed and do not depend on each other.

Display: present_trial() and get_response()

These two module-level functions are the most-used interfaces inside the trial loop. Both are thin wrappers around io.presenter:

# Display the trial (four blocks)
io.present_trial(
    trial,
    trial_number = i,
    total_trials = n,
    labels       = exp.labels,  # optional: show label hint line
    bar_width    = 28,          # character width of ASCII attribution bars
)

# Collect response + measure reaction time
response, rt = io.get_response(
    trial,
    timeout = 30,   # seconds; None = wait indefinitely
)
# response: stripped string, e.g. "Good Quality"
# rt:       float seconds from prompt display to Enter

Recording: DataRecorder

Accessed as exp.data after control.start(). Every call to record() immediately appends one row to the CSV, so a mid-session crash never loses data from completed trials.

Method / PropertyDescription
data.record(trial, response, rt)Writes response and rt to the trial object and immediately appends a CSV row.
data.save_summary()Generates the summary report (.txt) and returns its path. Called automatically by control.end().
data.csv_pathPath object pointing to the response CSV. Determined at start() time.
data.summary_pathPath object pointing to the summary report. Determined at start() time.

The swappable presenter interface

io.presenter is a global variable that defaults to TerminalPresenter(). Replacing it with any BasePresenter subclass switches the display backend — web page, GUI, tablet — without any changes to the trial loop.

from xai_tester.io._presenter import BasePresenter
import xai_tester.io as xio

class WebPresenter(BasePresenter):

    def show_trial(self, trial, trial_number, total_trials,
                   labels=None, bar_width=30):
        # Render trial data as an HTML page and push to browser
        ...

    def get_response(self, trial, timeout=None) -> tuple[str, float]:
        # Wait for HTTP POST; return (response_string, rt_seconds)
        ...

    def show_message(self, text: str):
        # Serve a plain text page
        ...

    def clear(self):
        pass   # no-op for web

# Assign before the loop — nothing else changes
xio.presenter = WebPresenter()

get_response() contract: must return a (str, float) tuple — the stripped response string and the reaction time in seconds. Return an empty string "" on timeout (which makes trial.is_correct evaluate to False).

Input Format

XAI Tester expects a fixed column-naming convention. Each row is one trial:

ColumnTypeDescription
yintAI predicted label as an integer code (e.g. 0/1). Converted to a display string via label_map and stored in trial.ai_label.
v0–v5anyRaw feature values. Mapped positionally to the names in feature_names.
a0–a5floatFeature attribution scores (SHAP / LIME output). Positive = pushes toward positive class; negative = pushes away. Must be convertible to float.
gt (optional)int/strReal-world outcome. Specify the column name via ground_truth_col="gt".
 
# Example CSV header (wine quality dataset)
y,v0,v1,v2,v3,v4,v5,a0,a1,a2,a3,a4,a5
1,0.44,16.0,3.55,0.39,11.4,6.43,0.0775,-0.0335,0.1186,-0.0575,0.1038,0.0083
0,0.58,37.9,2.99,0.42,10.3,4.99,-0.0327,0.0133,-0.0356,-0.0468,-0.1762,-0.0161

For Apple Numbers files (input_values.numbers), convert first using the bundled utility:

# Requires: pip install numbers-parser
python numbers_to_csv.py input_values.numbers output.csv
python wine_quality_study.py --csv output.csv
07

Output Files

Two files are written to xai_results/ (configurable via misc.defaults.data_directory). Both share the stem <experiment_name>_<participant_id>_<YYYYMMDD_HHMMSS>.

Response CSV (.csv)

One row appended per completed trial — immediately after data.record() is called. A mid-session crash loses no data from completed trials.

ColumnDescription
ai_labelAI predicted label for this trial.
ground_truthReal-world outcome. Empty string if not provided.
ai_agrees"True" / "False" / "" — whether the AI was correct.
responseParticipant's typed prediction (stripped).
is_correct"True" / "False" — whether the participant matched the AI label.
response_time_sReaction time in seconds.
feat_*Original feature values, prefixed feat_.
xai_*Attribution scores, prefixed xai_.

Summary report (_summary.txt)

Written by control.end(). Contains up to seven sections:

SectionConditionContent
Session headerAlwaysExperiment name, participant ID, trial counts, session duration.
Participant accuracyAlwaysCorrect / incorrect counts and percentage.
AI model accuracyWhen ground_truth presentHow often the AI label matched ground truth.
Accuracy by AI correctnessWhen AI has both right and wrong trialsParticipant accuracy on AI-correct vs AI-incorrect trials — the primary XAI research metric.
Response timesAlwaysMean, median, SD, min, max (seconds).
Per-label breakdownAlwaysTrial count, participant accuracy, and mean RT per AI label class.
Top features by importanceAlwaysFeatures ranked by mean absolute attribution score across all trials (up to 10).
08

Custom Presenter

The default terminal display is ideal for local experiments. For a web interface, iPad deployment, or any other display surface, subclass BasePresenter, assign it to xai_tester.io.presenter, and the trial loop code remains completely unchanged.

BasePresenter requires four methods to be implemented:

MethodResponsibility
show_trial(trial, trial_number, total_trials, labels, bar_width)Render the complete four-block trial display.
get_response(trial, timeout) → (str, float)Wait for input; return (response, reaction_time_seconds).
show_message(text)Display a plain-text message and block until Enter.
clear()Clear the current display.

Global Defaults

All configurable parameters live in xai_tester.misc.defaults. Override any value before calling control.initialise():

d = xai_tester.misc.defaults

d.response_timeout       = 30      # per-trial timeout (seconds); None = unlimited
d.pause_between_trials   = 0.4     # blank-screen pause between trials (seconds)
d.importance_bar_width   = 28      # character width of ASCII attribution bars
d.instructions_text      = "..."  # shown before the session starts
d.ready_prompt           = "..."  # appended below instructions_text
d.goodbye_text           = "..."  # shown at session end
d.data_directory         = "results"
d.summary_decimal_places = 3       # numeric precision in the summary report
